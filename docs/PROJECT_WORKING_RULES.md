# 项目协作规则

2026-10-09。参考 audio 项目的协作方式，按本项目已确认的 MVP 范围适配。本文件是协作规则的唯一维护位置，AGENTS.md 和 CLAUDE.md 仅指向这里。

## 分工与固定顺序

- 用户确定目标、业务取舍、授权阶段及必要外部操作。
- Codex 负责范围、规划、反馈处理、实际规格检验和集中复核；CC + Comet 是默认实施方。用户可以明确指定其他执行方。
- 新 Spec：Codex 规划 → CC 只读审阅 → Codex 修订 → CC 只编写 Spec → Codex 检验实际产物 → 独立实施提示词 → CC 实施 → Codex 集中复核。
- 规划和完整交接统一在 `docs/specNN/EXECUTION_PLAN.md`；反馈处理写 `review-notes.md`。聊天给文件入口和短的可复制 CC 提示词。
- 只读审阅不授权写文件、创建 change、安装依赖、运行测试或启停服务。
- 规格编写只授权正式规格与必要流程文件，校验后停止；不得写完 Spec 自动实施。
- 实施由独立提示词授权；当前范围内连续实现、基本检查和修复，不逐小步确认。
- 每轮只处理当前明确任务，不自动进入下一 Spec、提交、推送、部署或归档。

## CC 跨会话实施与集中返修

2026-10-19：同一功能、同一正式 change 允许跨多个 CC 会话完成；换会话不改变原规格、验收标准、授权阶段或停止点。

- **换会话时点：** 首次实施集中交付给 Codex 复核；若复核后仍需返修，每次 Codex 集中复核结束并整理本轮问题单后，默认由新的 CC 会话接续。每轮修复内部连续完成实现、自检和必要修复，不按单个问题、Edit 或测试重开，也不要求先把全部问题修完才能换会话。10→6→4→3→1的收敛及范围内新发现问题均可正常推进，不以问题总数判断是否停滞。
- **Codex 准备交接：** 复核后更新现有 `docs/specNN/EXECUTION_PLAN.md` 的最新执行入口；问题依据和关闭条件放在 `review-notes.md`，`SESSION_START.md` 只指向当前轮次与对应章节。保留原编号并区分已核实关闭、仍未解决、新发现及待核实项，避免已关闭问题被旧段落再次作为待办。正式 tasks 仍是唯一任务状态，不另建流程或任务账本。
- **每轮最小交接内容：** 项目目录、Spec/change、当前阶段/轮次和授权依据；原规格及当前停止点的文件入口；本轮问题编号、位置、关键反例和关闭条件；现有改动文件及需保护的未提交工作；关键测试命令、实际结果和证据路径（通过/失败/跳过/未运行分开，注明验证时对应的源码或输入）；已确认的排错结论、已排除方案及尚待验证的猜测；下一步及 UA 已覆盖或滞后范围。优先引用既有文件和必要章节，不复制全部历史对话、旧错误输出或每轮完整规格。
- **CC 集中执行与回传：** 在本轮已有授权内连续处理清单及本功能范围内新发现的问题；只为新增业务取舍、范围扩张、凭据或真实阻塞升级给用户。结束时在现有交接章节更新逐项实施结果、改动清单、关键验证证据和剩余问题，再停止写入交给 Codex；CC 自报已修复不等于 Codex 已核实关闭。Codex 复核当前问题和受影响行为，复用仍适用的稳定证据；源码、输入或环境变化使旧证据不适用时，补做必要验证。
- **新 CC 从当前状态接续：** 先确认旧 CC 已停止项目及图谱写入，轻量核对实际 Git/工作区和必要的 Comet/Runtime 状态，再按当前执行入口读取规格、问题单和相关代码。保留全部既有代码、测试及未提交改动，不重新开发、重新规划或重审已关闭规格，不擅自重置、清理、回滚、提交或切换 change。历史交接与现场不符时，以源码和当前有效证据核实并更正；换会话不代替授权，也不自动推进 Verify/归档等阶段。
- **启动与短提示词：** Codex 交付时明确标注“请使用新的 CC 会话”，并给出包含项目目录、文件/章节、目标、授权边界和停止点的短提示词；用户无需自行判断 token 或问题数。新开终端后仍使用 `-c`/`--continue`/`--resume` 或恢复历史会话，会继续携带旧上下文；本规则要求实际新建会话，同时保留本轮应使用的模型配置。只更新协作方法不授权重启或中断正在执行的 CC；新规则从下一次交接使用。
- **UA 辅助读取：** 新会话先查本轮相关图谱节点、摘要、函数行号和直接依赖，并按工作区指纹核对，再读取修复及验证所需的源码/测试片段。不要把整张图谱送入上下文，不因新会话全仓重读、全量重建或逐条 Edit 刷新。仍按下节每个实现/修复批次定向刷新一次；图谱辅助定位，不替代源码核实、返修交接或功能验收。无图项目不能宣称已享受图谱收益，也不因交接擅自建图。

## CC 排错与 Codex 复核

适用于每轮实施、自检和返修，沿用当前授权、问题单和集中复核；从下一次交接使用。

- **先看最早失败：** 出现非预期失败，先区分编译、测试脚本/夹具、环境或子进程启动失败，以及实际业务断言失败。读取原始异常、退出状态和相关 stderr，再追查缺失文件等后续症状。必要的完整关联输出留在本地，交接只给关键片段和路径；不能只保留 head/tail 而丢掉最早错误，也不输出凭据。原因已经明确时直接修复并验证，不为满足流程重复取证。
- **先核对接口与对照：** 返回值或状态不符合预期，先并排核对函数签名、调用接收位置和断言；已有通过的对照时，优先找两者的最小差异。未改的同一段代码已有有效读取结果时先复用，重新读取须有定位、核实修改或纠正上下文等明确目的。
- **验证原始失败内容：** 对生成脚本、配置和请求，直接读取或导出实际失败内容，必要时在临时目录清理前保存。脚本无法启动时先对该内容做静态语法检查。手工重写的副本须核对差异，副本通过不能替代原件验证；Python 仍使用项目指定解释器。
- **每次复跑有目的：** 相同代码和输入出现相同错误，先利用已有错误信息明确当前假设、下一项检查及预期结果，再做能区分原因的最小实验或修改。不无依据地轮换缓存、路径、环境和临时副本；为确认复现、时序或稳定性而重复运行可以继续，但应有明确目的。不按固定失败次数停止、重开会话或要求用户批准，范围内新问题仍连续处理。
- **修好后回到原验收：** 夹具恢复、静态解析通过、进程退出或任意非成功状态，都不能代替目标业务行为。回跑原失败用例及必要的受影响检查；受控停止等用例应核对具体原因和业务状态。编译失败、启动失败、业务断言失败、通过、跳过和未运行分别报告。
- **Codex 复核与交接：** 在既有集中复核中核对原问题是否到达目标断言、修复是否有对应证据，不以测试次数或 CC 自报作为关闭依据。沿用现有 review-notes/执行入口，只保留“问题编号—已确认原因或待验证假设—关键证据—下一步或关闭条件”，明确已排除路径，不复制全部试错历史，不另建排错阶段或任务账本。

## MVP 范围

- 需求以 `docs/requirements/`、讨论总结和 `docs/plans/MVP_SPEC_ROADMAP.md` 为依据；用户最新确认优先。
- 本项目固定 16 个 MVP Spec，只求当前流程正常可用，允许小范围简化。
- 2026-10-10 用户明确：本项目主要负责后台能力与接口；客户档案网页、手机页面和界面交互属于其他系统。本项目交付数据模型、业务处理、查询/写入接口及 Agent 后台调用能力，不把页面或真机体验作为完成条件。
- 2026-10-10 用户进一步明确核心目标：10.1 §8 的7工具与10.2 §5 的14工具，共21个；16个Spec围绕这些工具和必要业务处理拆分。前台Agent为调用方，本项目做最小调用适配，不自建完整对话Agent。
- PostgreSQL；原始信息保留；软信息矛盾保留双方，由经理判断；默认有效期 180 天，同事件新证据刷新新鲜度。
- 录音后置；开发可用模拟数据，行内仿真按杨浩侧表结构；客户业务资料归业务模块，经理偏好仍归前台Agent记忆，但记忆实现不在本轮。
- 完整10.3日程、10.4产品知识与草稿、经理记忆、主动问询移出本轮核心交付，原需求与讨论保留。触达冲突只检查实际可查询数据，未接入其他日程时明确标注，不增加完整日程工程。
- 开发阶段不做敏感分级管控、完整角色体系、专项性能/合规验证、独立 POC 或完善性建设。
- 普通技术细节由当前阶段的负责方推荐或决定，不变成连续用户确认。实施采用 direct 方式，保留证明当前功能可用所需的最小自检，不强制逐任务 RED/GREEN。
- 规划审阅、规格检验和实现复核是不同对象，各集中完成一次；不复制 audio 的复杂验收矩阵，不用测试数量代替功能结果。

## 目录与单一写入方

- 单工作目录、普通 Git 分支，不用 worktree；Codex/CC 可并行只读，同一时刻一个执行方写入。
- 开始前核对实际 Git、文件及服务状态，保留未提交改动；不自动 stash/reset/clean，不覆盖用户工作，不使用 `git add -A`。
- 全部组件先本地推进；外部 API 只在对应任务有明确授权时使用，部署另外安排。
- 样例、压缩包、数据库数据和本地凭据不随代码提交；不复制其他项目的私密配置或 Runtime 状态。
- 全部 Python 命令使用 `~/.claude/cc/bin/python`，安装使用配套 pip。

## CC 代码索引规定（优先定向刷新）

2026-10-13 用户调整：**能不用全量就不用。** 本节取代2026-10-10的逐次写入刷新频率及默认全量命令。继续使用 Understand Anything，图谱唯一位置为 `/home/pine/workspace/crm/.ua/knowledge-graph.json`。

1. **改动前轻量核对：** 对照当前工作区文件与内容指纹，查看本批次涉及的节点和直接依赖。匹配时复用现有分析，不重新建图；代码漏收或滞后时先定向补齐。不能只凭HEAD或时间戳判断，包括未跟踪代码。
2. **每批次刷新一次：** 同一明确实现切片或修复事项内，允许连续修改相关代码、测试及配置；在交付或开始下一无关批次前统一刷新。不按每条Edit/Write重复分析，也不等到提交时才刷新。
3. **默认定向：** 仅重分析本批次新增/修改文件，处理删除/重命名及受影响边；必要时核对直接邻居。保留其余有效节点、摘要、架构层级和导览，不重复调全图分析、架构分析或导览生成。确定性的清单、hash、结构提取和图完整性检查不等于全量语义重分析。
4. **全量例外：** 首次无图、图谱损坏到无法局部恢复，或实际大范围结构变化确实不能局部表达时，才执行全量，并记录具体理由和范围。脏工作区、HEAD未变、增量报错或工具阈值本身不构成全量理由；不得自动回退到 `--full`。
5. **失败与真实性：** 定向刷新失败时保留代码和旧图，记录未覆盖文件、具体错误及停止点；停止后续写码或交付，不伪报成功。必须按实际源码更新节点、依赖和语义摘要，不能只补hash/时间戳；已有分析经源码核对仍准确的部分可以保留。不因此重复业务自检或另建业务验收轮次。
6. **适用范围：** 业务代码、接口、测试、脚本及影响运行行为的配置。纯需求/规格/说明文档、索引接入配置和 `.ua/` 产物不触发刷新；索引若收录了这些文档，可在下一次定向刷新顺带更新其摘要，或明确记为文档滞后，不能把未核对内容标为已覆盖。
7. **单一写入方：** CC串行维护CRM图谱、Codex共读。设置 `UNDERSTAND_NO_WORKTREE_REDIRECT=1`；不复制其他项目图谱、不另开worktree、不临时提交/stash/清理代码、不修改插件源码来绕过限制。图谱辅助定位，不代替源码核对和必要自检。
8. **复用既有接入：** Spec02已完成首次建图，保留 `.ua/config.json` 的 `autoUpdate=true`、`outputLanguage=zh` 和 `.ua/.understandignore`。凭据、客户资料、运行数据及生成物继续排除。自动Hook主要在提交/新会话触发，不保证每次工作区修改都已覆盖。

本机UA 2.9.7的原生 `prepare-incremental.mjs` 拒绝相关未提交/未跟踪文件；删除 `--full` 并不能使它支持脏工作区。遇到此条件，不反复运行该入口，不编造 `--files` 等参数，也不改用全量。采用**工作区定向流程**：以现有发布图谱为基线，明确文件列表，复用UA的结构提取与文件语义分析，只合并受影响节点/边和指纹，按实际工作区快照记录覆盖。Spec05的具体步骤见 [EXECUTION_PLAN.md §17](spec05/EXECUTION_PLAN.md#173-工作区定向刷新步骤)。该流程是项目级组合步骤，不冒称插件原生增量成功。

`.ua/`写入若被Comet Guard阻止，只允许按官方项目级 `hook.allow_paths` 补入 `.ua` 并保留已有项，或报告真实阻塞；不能禁用Guard或改用Bash绕过被拒绝的写入。索引更新不另建Spec或任务账本，纯索引维护不推进Comet阶段。
